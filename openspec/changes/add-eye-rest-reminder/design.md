## 背景

keep-eyes 是仅面向 Windows 的本地桌面护眼应用。应用必须在后台持续计时，并在用眼时间结束前以明显但不过度刺激、且不妨碍正常工作的方式提醒用户休息。首版收敛为单一流程：顶部透明置顶紧凑提醒、用户主动开始休息后关闭显示器、独立休息倒计时完成后开始下一轮。

## 目标与非目标

**目标：**

- 建立可测试的提醒状态机，统一驱动计时、提前提醒、自动开始休息、延后和暂停，并在重启时重新开始计时。
- 在默认提前 30 秒的可配置时间点显示透明、置顶、不抢焦点且可操作的紧凑提醒面板，面板依据绝对用眼截止时间实时显示距离休息的剩余时间，并在用户未处理直至用眼截止时自动开始休息；用户点击“知道了”时仅隐藏提醒并保持原定截止时间不变，点击“跳过本次休息，继续当牛马”时取消本次休息并立即开始一轮完整的用眼计时。
- 用户选择开始休息后请求关闭显示器，但把休息完成完全交给应用的绝对截止时间和明确操作判断。
- 使用 Electron 提供系统托盘、本地持久化和 Windows 显示器电源操作。

**非目标：**

- 第一版不提供温和通知、提醒方式选择、Windows 锁定或全屏/演示/远程控制场景检测。
- 不提供医学诊断、治疗建议、账号、云同步或多设备统计。
- 不拦截用户输入，不模拟 Windows 系统界面，也不承诺阻止用户唤醒显示器。
- 第一版不支持 macOS 或 Linux。

## 技术决策

### 1. 使用 Electron、React 和 TypeScript

采用 Electron 主进程管理系统托盘、提醒窗口生命周期、本地持久化和 Windows 显示器电源操作；React 渲染进程负责设置、状态展示、透明动画和提醒交互；通过预加载脚本提供最小化、明确的 IPC 接口。

- **理由：** Windows 托盘、透明置顶窗口和主进程系统调用是 MVP 的关键能力；React 和 TypeScript 有利于快速构建并共享类型。
- **考虑过的替代方案：** Tauri 可以降低包体积和资源占用，但需要 Rust 和插件边界设计；WPF/WinUI 原生体验更好，但不符合以 TypeScript/React 快速交付的目标。

### 2. 使用单一且可持久化的提醒状态机

核心领域模块维护“用眼计时”“等待处理”“已延后”“已暂停”和“休息计时”状态；运行期间使用下一次用眼截止时间、提前提醒时间、暂停到期时间和休息到期时间驱动状态机；持久化用户设置，但不将运行中的计时快照作为重启恢复依据。所有界面与托盘命令都向状态机发送事件，不分别创建互相竞争的计时器。

```text
用眼计时 --到期--> 等待处理 --开始休息--> 休息计时 --完成/结束--> 用眼计时
    ↑                  |                         |
    |                  | 延后                    | 重启协调
    |                  ↓                         ↓
    +--------------- 已延后                   持久化快照

等待处理 --暂停--> 已暂停 --恢复--> 用眼计时
等待处理 --跳过本次休息--> 用眼计时（从当前时刻开始完整周期）
```

- **理由：** 状态转换可以独立使用 Vitest 测试，并避免托盘、提醒窗口和重启恢复产生重复提醒。
- **考虑过的替代方案：** 由每个窗口分别使用 `setInterval` 虽然简单，但难以避免重复、计时漂移和恢复不一致。

### 3. 使用绝对截止时间派生可见倒计时

主进程中的提醒状态机继续负责状态转换、绝对截止时间和持久化，并只在状态或截止时间发生变化时通过受限 IPC 通知渲染进程。渲染进程维护仅用于界面刷新的本地显示时钟，在用眼计时、等待处理、已延后、已暂停和休息计时状态下，使用“绝对截止时间减去当前时间”派生剩余时间并至少每秒重新渲染一次。提前提醒面板必须复用本轮用眼计时的绝对截止时间显示“距离休息还有”的倒计时，不得把进入等待处理的时刻或静态的 0 秒作为倒计时来源。窗口重新显示、应用从后台恢复或系统睡眠恢复后，界面必须直接依据当前时间重新计算，不通过累计减秒延续旧值；到期状态转换由主进程负责，渲染层只负责展示。

- **理由：** 保持主进程为计时状态的唯一权威来源，同时避免为了刷新一个数字而每秒发送 IPC；绝对截止时间计算也能避免渲染暂停、系统睡眠和定时器延迟造成累计漂移。
- **考虑过的替代方案：** 主进程每秒广播完整状态会产生不必要的 IPC 和持久化耦合；渲染进程对旧值持续减一秒会在窗口挂起、系统睡眠或事件循环阻塞后显示错误时间。

### 4. 使用透明、置顶且非阻塞的紧凑提醒面板

距离用眼截止达到用户配置的提前提醒时间时，主进程在当前活动显示器顶部创建并统一管理一个透明原生窗口承载的、置顶但不抢夺焦点的紧凑提醒面板。透明仅用于实现非交互区域的输入穿透，面板本身必须通过足够不透明的局部底色、描边和阴影形成清晰可辨识的窗口轮廓；面板只占用顶部短条区域，不得创建覆盖整个显示器工作区的视觉窗口，且按钮之外的区域不得阻止用户操作底层应用。面板提供开始休息、延后、暂停、“知道了”和“跳过本次休息，继续当牛马”操作。“知道了”沿用原关闭操作，只隐藏当前提前提醒，不改变用眼截止时间，也不开始休息、延后或暂停；原定截止时间到达后仍按既定流程正式提醒并开始休息。“跳过本次休息，继续当牛马”关闭当前提醒、取消本次休息且不请求关闭显示器，并以点击时刻为起点创建一轮完整的用眼计时；旧的截止事件必须失效，不能在随后再次触发本次休息。重复的同状态更新必须复用现有实例，且不得重新打开已由用户关闭的提前提醒。

- **理由：** 顶部紧凑面板可以保持提醒可见，同时避免全屏透明层遮挡内容、抢夺焦点或造成“霸屏”；统一控制器可避免残留窗口和重复提醒。
- **考虑过的替代方案：** 全屏视觉动画层即使鼠标穿透也会覆盖整个桌面并干扰视觉工作；普通可聚焦弹窗可能打断输入；系统通知不便承载开始休息、延后、暂停和关闭等完整操作。

### 5. 开始休息后请求关闭显示器，但不将显示器状态视为休息结果

用户在提前提醒面板选择开始休息，或提前提醒显示后未处理直至用眼截止时，先由状态机进入休息计时，再关闭整组提醒窗口，并通过主进程 Windows 显示器电源适配器异步请求关闭显示器。请求成功、失败或用户随后唤醒屏幕都不得改变休息截止时间；只有休息倒计时结束或用户明确提前结束休息，状态机才开始新的用眼周期。

- **理由：** 关闭显示器可减少继续观看屏幕的诱因，但硬件和用户输入都不可靠地反映是否真正休息；状态机计时是可测试且一致的完成依据。
- **考虑过的替代方案：** 将亮屏视为休息结束会让一次鼠标或键盘操作跳过休息；在提醒到期前自动关闭显示器会剥夺用户延后或暂停的选择。

### 6. 使用本地优先的设置和运行快照

使用应用专属本地存储保存用户偏好和设置。保存设置时进行范围校验；应用启动或重启时忽略上次运行中的状态快照，按照当前时间和已保存设置创建新的用眼计时，不恢复待处理提醒，也不回放错过的提醒。

- **理由：** 不需要账号或网络即可保存设置并满足重启后重新计时要求。
- **考虑过的替代方案：** 仅使用内存存储会在重启后丢失用户设置；远程存储会引入账户、网络和隐私问题。

### 7. 使用支持自定义路径和卸载数据选择的 Windows x64 安装器

使用 Electron 的 Windows 打包与安装器配置生成 Windows x64 `.exe` 安装程序。安装器必须显示默认安装目录并允许用户选择有效的自定义本地目录；安装后注册 Windows 标准卸载入口，并在安装目录保留卸载程序。用户设置和提醒状态必须存储在应用数据目录，而不是安装目录：因此普通卸载可安全删除程序文件而保留数据，彻底删除选项则由卸载器明确清理应用数据目录。

- **理由：** 用户需要常规 Windows 安装体验、可控安装位置和可恢复的本地偏好；把用户数据和程序文件分离可避免升级或卸载时意外丢失设置。
- **考虑过的替代方案：** 便携式压缩包不提供标准卸载和安装路径流程；把设置写入安装目录会在卸载、权限限制或更新时导致数据丢失或写入失败。

### 8. Windows x64 作为首版支持矩阵

首版构建、测试和发布 Windows x64 安装程序，并以 Windows 10 x64、Windows 11 x64 为正式兼容目标。ARM64 和 32 位 Windows 不进入首版发布测试矩阵；Windows 7/8/8.1 不支持。

- **理由：** Windows x64 覆盖主要 Intel/AMD 桌面设备，能够控制首版打包、原生系统调用和测试范围。
- **考虑过的替代方案：** 同时发布 ARM64 会增加打包、原生依赖与真机验证成本，后续可在独立 Change 中增加。

## 风险与权衡

- **风险：** Windows 显示器电源行为会因硬件、电源策略和驱动不同而变化。**缓解：** 将关闭显示器视为尽力而为；失败后继续保持休息计时，不据此改变状态。
- **风险：** 透明窗口、置顶行为或鼠标穿透可能受 Windows 合成器、显卡驱动或多显示器环境影响。**缓解：** 使用普通置顶可操作窗口作为降级路径，并在 Windows 10/11 上手动验证。
- **风险：** 透明动画过强会造成额外视觉刺激。**缓解：** 仅使用平缓呼吸、渐变或等效低频动画，禁止快速闪烁和高频颜色切换。
- **风险：** 应用运行期间睡眠和系统时间变化可能造成计时漂移。**缓解：** 使用绝对到期时间，在运行中恢复时重新计算；应用重启则明确丢弃旧计时并重新开始。
- **风险：** Electron 可能带来较大的安装包和内存占用。**缓解：** 首版优先交付可用性，后续再评估 Tauri 或优化打包体积。

## 迁移计划

1. 从空仓库初始化 Electron、React、TypeScript 和测试工具链。
2. 先实现并测试不依赖界面的状态机、设置校验、用户设置持久化和重启后重新开始计时。
3. 添加主进程托盘、受限 IPC、顶部紧凑提醒窗口控制器和设置窗口。
4. 接入透明置顶且非阻塞的紧凑提醒面板、实时剩余时间、“知道了”和“跳过本次休息，继续当牛马”按钮、开始休息后的关闭显示器操作和失败降级，并逐项测试。
5. 在 Windows 10/11 环境手动验证多显示器定位、不抢焦点、底层应用可继续操作、关闭提前提醒后保持原计划、睡眠恢复、唤醒后继续休息、暂停和重启后重新开始计时。
6. 配置 Windows x64 `.exe` 安装包、安装路径选择、Windows 卸载入口和本地数据清理选项。
7. 在干净的 Windows 10 x64 和 Windows 11 x64 环境验证默认安装、自定义路径安装、普通卸载、彻底删除数据卸载和重新安装恢复。
8. 完成签名和打包前检查后发布首个本地安装包。

**回滚策略：** 如果透明紧凑提醒在特定设备上出现兼容性问题，控制器回退为普通置顶专注提醒窗口；核心计时、休息和本地设置不依赖服务器。

## 可延后的问题

- 紧凑提醒面板的具体颜色、圆角和低刺激动效可在界面设计阶段确定，只要保持透明可见、可交互、不抢焦点且不覆盖整个桌面。
- 提前提醒时间的精确最大值可在可用性测试后调整；首版支持 0～300 秒，默认 30 秒。
- 是否按应用窗口、鼠标所在位置或最近活动显示器选择目标屏幕，可在多显示器测试后确定；首版必须始终选择一个当前活动显示器。

## 后续修订决策

### 托盘图标

Windows 系统托盘必须始终显示可识别且非空白的 keep-eyes 图标。主进程使用由应用自身携带的图像数据创建 Electron `Tray`，避免开发运行目录、安装路径或资源复制方式变化导致图标路径失效。创建托盘前必须检查 `nativeImage` 是否为空；若图标创建失败，应明确报错，不得静默生成空白托盘项。

### 提前提醒“知道了”语义

提前提醒面板将原“关闭”按钮的显示文案改为“知道了”，其功能与原关闭操作完全相同。“知道了”只隐藏本次提前提醒，不进入休息、不延后、不暂停，也不修改原定用眼截止时间。控制器在当前等待处理阶段记录用户已确认的状态，避免相同状态更新、系统恢复或窗口刷新立即重新弹出；当状态离开等待处理阶段后清除该标记。原定截止时间到达时，状态机仍按既定规则进入正式休息流程。

### 跳过本次休息语义

提前提醒面板提供“跳过本次休息，继续当牛马”操作。该操作是明确的状态机事件：关闭当前提醒，取消即将发生的本次休息，不请求关闭显示器，并从用户点击时刻开始一轮完整的用眼计时。调度器必须撤销或使旧用眼截止事件失效，避免旧事件在新周期内再次触发休息；该操作与“知道了”不同，不保留原定截止时间。

### 非阻塞窗口边界

提前提醒只创建一个位于活动显示器顶部的紧凑透明面板，不再创建覆盖整个显示器的动画层。窗口保持置顶但不可聚焦，并通过非激活方式显示，以保证用户可以继续操作底层应用。只有面板自身及其按钮接收交互，窗口尺寸必须限制在提醒内容所需范围内。
